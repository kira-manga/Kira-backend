## Bounds and qualification limits

Both the complete unsigned manifest **and complete signed envelope**, with its
fixed SINGLE 384-byte RSA-PSS signature, must fit
`min(131072, configured reader maximumEnvelopeBytes)`. Signature overhead is
checked before PREPARE using a size-only placeholder that cannot authorize Sign
or PUT. The same paid limits apply to reload/recovery. Full inventory/evidence is
never dropped to fit. The separately configured manifest-record, generation,
aggregate chain-byte, parser and reader deadlines still apply.

A syntactically valid large run may not fit. The general 8-MiB catalog ceiling and
4096-chunk domain limit are not terminal paid permission. No reserve increase,
pagination, maximum-N liveness proof or support for every syntax-admitted history
is claimed. The exact-131072 TEST specimen is deliberately a **size-only** inventory
variant; the full producer chain must reject it because its inventory changed.

The current preflight rereads bounded history per native version: **O(R²)** overall,
with each SQL phase capped at 2 seconds. The fresh aggregate attempt budget is
`2 * scanMillis + activation.totalAttemptMillis +
3 * min(readback.totalAttemptMillis, 10000) + 24000` milliseconds. Per-version
preflights consume the native allowance, not a renewal. The genuine catalog lease
also has a fixed 30-second lifetime after acquisition. These are refusal bounds,
not worst-case scheduling, performance or maximum-size acceptance qualifications.

## Exact PREPARED continuation and failure boundaries

Recovery repeats fresh raw-evidence admission, current checks, both native pairs,
full raw chain observations and exact external-custody validation. It may not
rebase, change signer policy, replace a frozen witness, reprice or acquire a
replacement operation token. A fresh genuine lease is compared to every retained
old arm before any new arm is added.

| Existing durable state | Allowed continuation |
|---|---|
| Paid PREPARED; no SIGN arm | First Sign of the exact frozen bytes only, after fresh admission. |
| Old SIGN arm, no durable returned signature | **Refuse another Sign.** The outcome is not reconstructed from absence of a signature; no automatic recovery/acceptance is claimed for this unresolved cut. |
| Durable signature, possibly missing envelope/return leaf or SQL acknowledgment | Verify and reuse the exact signature; fill only absent consistent leaves or the write-once SQL field. Never re-Sign. |
| Old PUT arm, keys absent or source-only | Never PUT again. Source-only stays PREPARED; absence after an old arm is not permission to repeat. |
| Exact dual copy, COMPLETE absent/unknown | Fresh actual dual proof may complete the original mutation only. |
| Exact COMPLETE/pending token, PROJECT absent/unknown | One token-bound projection with no second payment or audit. |
| Exact already PROJECTED | Fresh checks/native observations, then **read-only** confirmation. No ACQUIRE/RELEASE, owner/lease/timestamp/xmin/payment/Sign/PUT/COMPLETE/PROJECT or custody-file churn. |

The no-repeat-Sign rule is deliberately more conservative than the proposal's
possible “Sign finished but not retained” continuation; this source provides no
authority to repeat an uncertain Sign. A failed/UNKNOWN/cleanup-uncertain original
remains failed. Failure is not erased by closing another process, observing elapsed
time or recovering its durable effects from a new original. A declared or measured
timeout is not proof of native resource retirement.
